# Архитектура

## Компоненты

```
Браузер ──► Caddy (HTTPS) ──┬─► frontend (Next.js, :3000)
                            └─► backend  (FastAPI, :8000) ──► PostgreSQL
                                     ▲                     └─► Redis
worker (ARQ, cron) ──────────────────┘   hh.ru API, AI-провайдер, Telegram — только из backend/worker
```

| Компонент | Роль |
| --- | --- |
| `backend/app/api` | HTTP-роуты, только проверка прав и сериализация |
| `backend/app/services` | Вся логика: интеграция hh.ru, матчинг, письма, отклики, автоматизация, аналитика |
| `backend/app/models` | SQLAlchemy 2, миграции в `backend/migrations` (Alembic) |
| `backend/app/workers` | ARQ: тик планировщика каждые 5 минут, рассылка в Telegram, ночная очистка |
| `frontend/src` | Next.js App Router, клиентские страницы поверх REST API |

## Основной сценарий: без API hh.ru

С 15.12.2025 соискательский API hh.ru закрыт для сторонних приложений (подробно в
[hhru_api_capabilities.md](hhru_api_capabilities.md)). Поэтому основной путь работает без него:

1. Вакансия попадает в Ashore закладкой из браузера (`/clip`, данные идут во фрагменте URL) или вручную.
2. Матчинг оценивает её локально и объясняет оценку.
3. Письмо собирается только из фактов резюме и проходит проверку.
4. Отклик: письмо копируется, открывается форма hh.ru, пользователь отмечает отправку в CRM или Telegram.
   Такой отклик хранится с `confirmed_by = user` и в аналитике не выдаётся за подтверждённый hh.ru.

Если ключи API появятся, тот же код включает поиск, отклики и статусы через API — но только для операций,
которые hh.ru реально разрешил этому аккаунту (`IntegrationCapability`).

## Проверка возможностей hh.ru

`services/hhru/capabilities.py` хранит статус пяти операций: поиск, чтение резюме, чтение откликов,
отправка отклика, поднятие резюме. Безопасные GET проверяются сразу после подключения. Отклик и
поднятие необратимы, поэтому не «пробуются»: статус `verified` они получают только после первого
успешного запроса, подтверждённого пользователем. Ответ 403 переводит операцию в `unavailable`, и
интерфейс переключается на ручной путь.

## Матчинг

`services/matching`:

* **Жёсткие фильтры**: архив, стоп-лист компаний и слов, зарплата ниже минимума (если указана),
  регион и формат, тип занятости, опыт, признаки мошенничества. Неуказанная зарплата — риск, а не отказ.
* **Оценка 0–100** из шести компонентов с настраиваемыми весами: навыки (пересечение + локальное
  семантическое сходство), опыт, должность, зарплата, формат/регион, образование.
* **Решение**: `reject` / `review` / `eligible` по порогам профиля поиска; противоречивые требования и
  тесты работодателя отправляют вакансию на ручную проверку.
* **AI** (если разрешено): второе мнение, которое сдвигает оценку не больше чем на ±10 и не может
  отменить жёсткий фильтр.

## Отправка откликов

`services/applications/engine.py`:

* Один отклик на вакансию: уникальный индекс `(user_id, vacancy_id)` и ключ идемпотентности.
* Write-ahead: перед запросом к hh.ru статус `sending` фиксируется в базе.
* Таймаут или 5xx после отправки дают `unknown`, а не повтор. Перед любой новой попыткой отклик
  сверяется через `GET /negotiations`; если читать отклики нельзя, пользователя просят проверить.
* `already_applied` считается успехом, `limit_exceeded` и капча ставят автоматизацию на паузу,
  403 переключает на ручной путь.

## Режимы автоматизации

| Режим | Что делает система |
| --- | --- |
| Ручной | Оценивает и готовит письма по кнопке |
| С подтверждением | Сама готовит очередь, отправка только после «да» в вебе или Telegram |
| Автоотклики | Отправляет по правилам. Нужны: подтверждение правил (хэш правил), `apply = verified`, дневной лимит ≤ 50, окно отправки |

Любое изменение правил меняет хэш и выключает автоотклики до нового подтверждения. Кнопка
«Остановить всё» ставит паузу и возвращает очередь на подтверждение.

## Планировщик

`ScheduledJob` в PostgreSQL — источник правды. Тик берёт задачи через `FOR UPDATE SKIP LOCKED` и
сдвигает `next_run_at`, поэтому два воркера не выполнят одно и то же. Задачи одного пользователя
сериализуются Redis-блокировкой. Ошибки дают экспоненциальную задержку до 24 часов.

## Деградация

* Redis недоступен: ограничение частоты переходит на память процесса, блокировки пропускаются
  (корректность держится на ограничениях БД), `/api/health/ready` отвечает `degraded`.
* hh.ru недоступен: circuit breaker на подключении, после порога ошибок запросы приостанавливаются.
* AI недоступен или нет согласия: используются локальные алгоритмы, ничего не ломается.
